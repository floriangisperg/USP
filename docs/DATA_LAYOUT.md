# How data is organised

USP the **package** is folder-agnostic — `load_config` + the parsers take
whatever paths you give them. But every example script follows one layout
convention, and reusing those scripts (recommended, see
[YOUR_OWN_DATA.md](YOUR_OWN_DATA.md)) means following it too. This page is
the canonical description.

## The two levels

```
<campaign>/                       # one campaign = one experiment series
├── <campaign>_consolidated_results.xlsx      # generated by consolidation
├── <campaign>_consolidated_dashboard.html    # generated
│
├── <run_id>/                     # ── one folder per fermentation ──
│   ├── run_config.yaml           # run settings (COMMITTED) — lives HERE,
│   │                             #   next to data/, never inside it
│   ├── data/                     # raw inputs (gitignored)
│   │   ├── <anything>.csv        #   online bioreactor export (name free)
│   │   └── samples.xlsx          #   offline lab measurements
│   └── results/                  # generated outputs (gitignored, auto-created)
│       ├── processed_data.csv    #   aligned + derived time series
│       ├── samples_points_data.csv
│       └── <param>_timeseries.png
│
├── <run_id>/                     # next fermentation
└── ...
```

The pipeline and consolidation are package entry points — no per-example
scripts: `python -m upstream_analysis.pipeline <run_dir>` analyzes one run,
`python -m upstream_analysis.consolidation <campaign> --prefix <P>` builds
the consolidated workbooks and dashboard.

Real examples of this layout: `examples/hgh/` (cleanest — two runs),
`examples/scFvM/` (13 runs + `all_data/` raw campaign exports),
`examples/LDH/` and `examples/Xiso/`. A single-fermentation analysis is the
same minus the campaign level — that is what
`python scripts/new_run.py <name>` scaffolds under `runs/`.

## What actually has to be where

| Item | Location | Required? | Notes |
|---|---|---|---|
| `run_config.yaml` | `<run_id>/` (root, **next to** `data/` — not inside it: `data/` is gitignored, the config is what git tracks) | required by the scripts | name/position fixed; contents mostly optional (only `initial_volume_ml` is mandatory) |
| online export | `<run_id>/data/*.csv` | required | **filename is free** — scripts auto-detect the single CSV |
| offline measurements | `<run_id>/data/samples.xlsx` | optional | conventionally named `samples.xlsx` (scripts glob for it); absent → pipeline runs online-only |
| `results/` | `<run_id>/` | auto-created | never commit; delete freely and re-run |

Run IDs are free-form (`ferm_01`, `R5_lowlow`, `F19`, `00_Ferm01` all exist).
Campaign-level reference files (media sheets, pump calibrations, operator
evaluation workbooks such as `Evaluation_F19.xlsx`) sit next to the runs —
either at campaign level or in the run folder they belong to; reference
them from `run_config.yaml` by relative path if the pipeline reads them
(e.g. `induction_reference_file`).

## Campaign-level outputs

`python -m upstream_analysis.consolidation <campaign> --prefix <P>` reads
every `<run_id>/results/processed_data.csv`, tags rows with a `run_name`
column and writes, at campaign level:

- `<campaign>_consolidated_results.xlsx` — all time points + per-run summary sheets
- a `_sparse` variant with sample points only
- an interactive `<campaign>_consolidated_dashboard.html` (bokeh; `dashboard` extra)

## What git tracks

By policy (enforced by `.gitignore` extension rules), the repo tracks
**configs and written notes** — `run_config.yaml`, correction docs — and
ignores **all data and outputs**: `data/`, `results/`, raw campaign
exports, consolidated workbooks, plots. No example ships data; the
end-to-end coverage lives in the test suite (synthetic run fixture).

## Growing from one run to a campaign

1. Scaffold and analyze your first run (`scripts/new_run.py`,
   [YOUR_OWN_DATA.md](YOUR_OWN_DATA.md)).
2. When the next fermentation starts, create `<campaign>/<run_id_2>/` with
   its own `data/` + `run_config.yaml` (copy the first one and adjust).
3. Run the pipeline on each run folder, then consolidate:

   ```bash
   for d in <campaign>/<run_id_*/; do python -m upstream_analysis.pipeline "$d"; done
   python -m upstream_analysis.consolidation <campaign> --prefix <campaign>
   ```
